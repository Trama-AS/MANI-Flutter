# MANI — Contexto de Arquitectura para Agente de Desarrollo

> Documento de handoff técnico. Compilado a partir del SAD (MANI-SAD.xlsx), el inventario de ADRs, el CSV de Escenarios de Calidad y el formato de ADR del proyecto TRAMA · Ingeniería de Software. Los vacíos de información se marcan explícitamente con 🔴 — no se rellenan con supuestos.

---

## 1. Identidad del proyecto

- **Nombre:** MANI
- **Equipo:** TRAMA · Ingeniería de Software
- **Tipo:** Proyecto académico de arquitectura de software (metodología ADD/ATAM, marco de calidad ISO/IEC 25010:2023)
- **Propósito:** Plataforma SaaS multi-tenant que formaliza el ciclo de vida de servicios entre clientes, aliados (proveedores de servicio) y empresas tenant, reemplazando la coordinación informal actual vía apps de mensajería.

## 2. Actores del sistema

| Actor | Rol |
|---|---|
| Cliente | Solicita servicios |
| Aliado | Proveedor de servicio aliado del tenant |
| Administrador de tenant | Administra la configuración y operación de su empresa (tenant) |
| Administrador de plataforma | Administra tenants a nivel de toda la plataforma |

## 3. Alcance funcional

- **MVP (1er incremento):** RF-01 a RF-23
- **2º incremento (fuera de alcance del MVP):** RF-24 a RF-28 — pagos, quejas/reclamos, comercialización
- 🔴 **Gap:** el listado detallado de cada RF-01 a RF-28 (nombre, descripción, criterios de aceptación) no está disponible en esta sesión — vive en el workbook `MANI-SAD.xlsx` (hoja no incluida aquí). Los RF solo se conocen por referencia cruzada desde la hoja `Escenarios_Calidad` (sección 8).

## 4. Gobernanza (aplica al proceso, no a la arquitectura en sí)

- Modelo **Mesa de Arquitectura**: quórum de 5/7, disidente obligatorio, disenso documentado.
- **Ninguna decisión (ADR) es válida hasta ser ratificada por la Mesa**, incluidas las generadas o sugeridas por IA.
- Toda sugerencia de ADR generada por IA se marca explícitamente **"Propuesto"** con disclaimer de asistencia de IA (regla fijada en ADR-0009).
- Estas reglas de gobernanza son proceso de equipo, no drivers arquitectónicos — no deben mezclarse con la sección 6/7.

## 5. Stack tecnológico

### 5.1 Stack ratificado (ADR-0012)

| Capa | Tecnología |
|---|---|
| Backend | Dart / Serverpod |
| Base de datos | Supabase (PostgreSQL con Row-Level Security — RLS) |
| Cliente | Flutter (código único Android/iOS) |

### 5.2 🔴 Contradicción activa de stack — bloqueante para un agente de código

- **ADR-0004, ADR-0005, ADR-0006** están en estado **Aceptado** y describen un stack **Java / .NET / Azure**.
- Este stack es **mutuamente excluyente** con el de ADR-0012 (Dart/Serverpod + Supabase + Flutter), y **ninguno de los dos conjuntos ha sido formalmente superseded**.
- Riesgo documentado como **KI-01**: contradicción Dart/Serverpod vs. requisito curricular Java/.NET.
- Riesgo documentado como **KI-02**: Kubernetes tratado como opcional pese a ser una restricción curricular no negociable — **no tiene fila propia en la hoja Killers pese a citarse 3 veces en la hoja ADR** (issue de integridad de datos).
- **Implicación práctica para el agente de código:** antes de generar cualquier código de infraestructura o backend, el proyecto debe resolver cuál stack es el vigente. No asumir Dart/Serverpod por defecto sin confirmación — hay dos conjuntos de ADRs "Aceptado" en conflicto real.

## 10. Formato estándar de ADR (para generar nuevos)

```markdown
# ADR-NNN: <título breve de la decisión>

- Fecha: AAAA-MM-DD
- Sprint: <n>
- Autor: <nombre y rol>
- Origen: <Mesa Técnica | Sprint Planning | issue #NNN>
- Revisor: <integrante distinto del autor que aprueba el pull request>

## Contexto
<Fuerzas en tensión: técnicas, de proceso, de negocio y de plazo académico. Lenguaje neutral, solo hechos.>

## Alternativas evaluadas
1. <Opción A> — descartada porque <motivo objetivo y verificable>.
2. <Opción B> — descartada porque <motivo objetivo y verificable>.
<Mínimo dos alternativas reales.>

## Decisión
Usaremos <...>.
<Una sola frase, voz activa, primera persona del plural. Sin condicionales.>

## Trade-off asumido
<Lo que el equipo sacrifica conscientemente: costo, tiempo, acoplamiento, portabilidad o deuda técnica.>

## Estado
<Propuesto | Aceptado | Obsoleto | Reemplazado> — última actualización: AAAA-MM-DD

## Consecuencias
- Positivas: <...>
- Negativas: <...>
- Neutras: <...>

## Trazabilidad
- Issues: #<n>
- Pull requests: #<n>
- Componentes del modelo C4 afectados: <contenedor o componente>
- Documentos que deben actualizarse: <instructivo, guía de contribución, estrategia de pruebas>
```

**Checklist antes de abrir el PR (Gobierno del Equipo, sección 2.6):**
1. Los siete campos presentes, sin marcadores `<...>` sin reemplazar.
2. La decisión cabe en una frase y no admite dos lecturas.
3. Al menos dos alternativas descartadas con motivo verificable.
4. Al menos una consecuencia negativa o neutra.
5. Estado único, fechado y enlazado si corresponde.
6. Enlazado al issue y al pull request de implementación.
7. Revisado por un integrante distinto del autor.

## 11. Repositorio y convenciones técnicas

- **Repo:** `Trama-AS/MANI-docs` en GitHub (organización: `github.com/Trama-AS`)
- Acceso a contenido raw: `raw.githubusercontent.com/Trama-AS/MANI-docs/main/[carpeta]/[archivo]`
- La API de GitHub es poco confiable por rate limiting; parsear la página HTML del árbol de archivos es más estable.
- Extracción de Excel: `openpyxl` con `data_only=True`. Layout de hoja: fila 0 = título, fila 1 = subtítulo, fila 2 = encabezados, filas 3+ = datos.
- Pipeline PDF: `pandoc` (md → HTML5, `--standalone -c style.css`) → `weasyprint` (HTML → PDF).

## 12. Principios de trabajo (aplican también al agente de código)

- **Disciplina de evidencia estricta:** drivers, killers y decisiones arquitectónicas deben respaldarse en ADRs o artefactos documentados — no rellenar vacíos con supuestos.
- **Los vacíos se marcan explícitamente** (🔴 o `<...>`) en vez de inventarse.
- **Integridad de datos sobre corrección silenciosa:** si el dato fuente tiene un problema, se documenta — no se corrige sin avisar.
- Ningún ADR (ni humano ni generado por IA) es válido para implementación hasta ser ratificado por la Mesa de Arquitectura.
